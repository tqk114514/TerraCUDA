## 1. 线程地图（26.1.2 实码）

执行器拓扑由三处代码定死：

- `MinecraftServer:373`：`this.executor = Util.backgroundExecutor()` —— 共享后台 ForkJoinPool
  （N−1 线程，规划文档 §60 已记录其容量公式）。
- `ChunkMap` 构造器（196–200 行）：
  ```java
  ConsecutiveExecutor worldgen = new ConsecutiveExecutor(executor, "worldgen");
  ConsecutiveExecutor light    = new ConsecutiveExecutor(executor, "light");
  this.worldgenTaskDispatcher = new ChunkTaskDispatcher(worldgen, executor);
  this.lightTaskDispatcher    = new ChunkTaskDispatcher(light, executor);
  ```
  两条任务车道 + 各自的簿记车道，**全部架在同一个后台池上**。
- `DistanceManager` 构造器（55–56 行）：
  ```java
  TaskScheduler<Runnable> mainThreadTaskScheduler =
      TaskScheduler.wrapExecutor("player ticket throttler", mainThreadExecutor);
  this.ticketDispatcher = new ThrottlingChunkTaskDispatcher(mainThreadTaskScheduler, executor, 4);
  ```

`AbstractConsecutiveExecutor` 是全部"串行车道"的实现基础：`SLEEPING→RUNNING` 的 CAS
（115–121 行）保证**同一时刻底池上只有一个任务在飞**——`run()` 只弹一个任务，跑完才重新
注册自己。所谓"worldgen 单车道"不是线程数限制，是这个单飞状态机。

| 通道 | 单飞机制 | 上面跑什么 | 耦合的主线程 |
|---|---|---|---|
| 主线程（"Server thread"） | tick 节拍 | 票务簿记、`runAllUpdates`、满块晋升回调、FULL 阶段体 | — |
| "worldgen" 车道 | ConsecutiveExecutor CAS | 生成任务续体 + **同步阶段体** | `runGenerationTasks` 按 tick 泵送入场 |
| "light" 车道 | 同上 | 光任务批（≤1000/批，`ThreadedLevelLightEngine:33`） | — |
| "dispatcher" 簿记车道 ×2 | PriorityConsecutiveExecutor（4 优先级） | 优先队列的 submit/release/resort/pop | `onLevelChange` 由主线程票务触发 |
| 玩家票节流车道 | ThrottlingChunkTaskDispatcher | 票的加/删簿记，**车道=主线程**，max=4 | 全部 |
| 后台池本体 | — | NOISE/BIOMES 的 `supplyAsync` 逃逸、光计算逃逸、我们的 GPU 接管 | — |

## 2. 每区块关键路径：一次生成 = 十几次单车道往返

完整链条（代码位置全部落在 26.1.2）：

1. 请求/票 → `GenerationChunkHolder.scheduleChunkGenerationTask` → `rescheduleChunkTask`
   → `ChunkMap.scheduleGenerationTask:666` —— 任务进 `pendingGenerationTasks` 列表。
2. **tick 泵**：`ServerChunkCache.runDistanceManagerUpdates:288` → `ChunkMap.runGenerationTasks:683`
   把列表里的任务逐个 `worldgenTaskDispatcher.submit(...)`。入场按 tick 节拍。
3. `ChunkMap.runGenerationTask:672` 提交的就是任务续体本身：
   ```java
   this.worldgenTaskDispatcher.submit(() -> {
       CompletableFuture<?> future = task.runUntilWait();
       if (future != null) future.thenRun(() -> this.runGenerationTask(task));
   }, chunk.getPos().pack(), chunk::getQueueLevel);
   ```
   `ChunkGenerationTask.runUntilWait`（45–59 行）是状态机：等上一层 future → 全完成则推进
   下一层 → 有未完成的就把它返回。**层完成后续体重新走一遍整个提交/排队/弹出流程**。
4. `ChunkTaskDispatcher.scheduleForExecution:88`：弹出一个区块的一批任务后，
   `CompletableFuture.allOf(...).thenAccept(r -> this.pollTask())` —— **该区块整批全部完成
   前不弹下一个区块**（整批 allOf 耦合）。
5. 每层 `scheduleLayer:117` 对半径矩形内每个 holder `applyStep`；中心跑体，邻居大多已被
   别的任务推进过——`GenerationChunkHolder.acquireStatusBump:219` 的 CAS 让输家直接挂到
   赢家的 future 上（波纹去重）。
6. 到达目标 → `releaseClaim`（释放 289 个 holder 的引用计数）→ 各状态 future 完成 →
   满块晋升回主线程 → 玩家票的节流槽在 `getEntityTickingChunkFuture` 完成时于主线程释放
   （`DistanceManager:101-102`）。

**我们自己的测量如何映射**（§13 补测）：今天 mod 场噪声 p50 只有 78 ms，但端到端
吞吐 85.7 cps @ cap 50 → 每区块管线内停留 ≈ **583 ms**——NOISE 之外的部分（其余阶段体、
单车道排队、波纹等待、FULL 的主线程节拍）占 ~500 ms。**这就是要动调度层的量化依据。**

## 3. 十二阶段语义表（`ChunkPyramid.GENERATION_PYRAMID` + `ChunkStatusTasks`）

| 状态 | 任务 | 写半径 | 直接依赖（半径） | 体在哪跑 |
|---|---|---|---|---|
| EMPTY | 载入 | — | — | IO 工作队列 |
| STRUCTURE_STARTS | generateStructureStarts | −1 | 父状态 | worldgen 车道（同步） |
| STRUCTURE_REFERENCES | generateStructureReferences | −1 | **STARTS@8** | worldgen 车道（同步） |
| BIOMES | generateBiomes | −1 | STARTS@8 | **supplyAsync → 池 "init_biomes"** |
| NOISE | generateNoise | **0** | STARTS@8, BIOMES@1 | **supplyAsync → 池 "wgen_fill_noise"**（我们接管处） |
| SURFACE | generateSurface | **0** | STARTS@8, BIOMES@1 | worldgen 车道（同步） |
| CARVERS | generateCarvers | **0** | STARTS@8 | worldgen 车道（同步） |
| FEATURES | generateFeatures | **1** | STARTS@8, CARVERS@1 | worldgen 车道（同步） |
| INITIALIZE_LIGHT | initializeLight | −1 | 父状态 | 光引擎 |
| LIGHT | light | −1 | INIT_LIGHT@1 | 光引擎 |
| SPAWN | generateSpawn | −1 | BIOMES@1 | worldgen 车道（同步） |
| FULL | full | −1 | 父状态 | **supplyAsync → 主线程执行器** |

要点：

- **NOISE 体本来就逃逸车道**（`NoiseBasedChunkGenerator.fillFromNoise:368` →
  `supplyAsync(..., "wgen_fill_noise")`:377）。车道上只剩一个等待者。**因此我们的 GPU 接管
  完全不减轻 worldgen 车道**——它解放的是后台池的 11 个核（§13 的"CPU 让渡"收益），
  而车道吞吐由其余同步体决定。这一条解释了 1.11× 的全部谜底。
- 写半径 0 = 只写自己（SURFACE/CARVERS 的体天生可并行）；写半径 1 = FEATURES 写 3×3。
- `ChunkGenerationTask` 创建时就按最坏半径**预取整个 StaticCache2D**（`create:36-42`，
  FULL 目标 → 半径 8 → **289 个 holder** 的引用计数进/出各一次）——任务声明即占坑。
- 双金字塔：`LOADING_PYRAMID` 全 passThrough（除光/FULL），配合
  `canLoadWithoutGeneration:86`——从盘载入的区块能跳过生成体。真实服务器是载入/生成混合流。

## 4. 串行化点全账单（逐个给代码 + 实测）

1. **worldgen 车道单飞**——同步体（SURFACE/CARVERS/FEATURES/SPAWN/结构两步）串行。
   实测：`-Poffload` 把半径 0 体挪下车道后，客户端噪声吞吐 67→99/s（**+48%**，§10 ④）。
2. **整批 allOf 耦合**（`scheduleForExecution:88`）——A 区块整批完成前不弹 B 区块。
   实测：parallelSched 打散它后端到端持平、p50 108→67–86 ms（§19 记录在备份分支）——
   **是延迟杠杆，不是吞吐杠杆**（cap 50 下吞吐=dwell 决定）。
3. **层间往返**——每次层完成都重新排队（`runGenerationTask` 的 thenRun 链）。
   与 #2 同源，同属延迟路径。
4. **tick 耦合**——三处：入场泵按 tick（#2 步骤）；FULL 体在主线程执行器（表 #3）；
   票务簿记/节流释放都在主线程（§2 步骤 6）。实测 FULL 主线程节拍均摊 ~25 ms/区块。
5. **玩家票节流器**——4 ÷ (票→entity-ticking 停留)（`DistanceManager:101-102` 槽位释放
   语义 + `maxChunksInExecution=4`）。实测非墙（§8 实验矩阵，无头 Chunky 完全不经过它），
   但客户端场景它决定"区块来得晚"的体感。
6. **波纹半径**——STRUCTURE_REFERENCES/BIOMES/NOISE 等层都要求 STARTS@8（17×17 邻域），
   新鲜邻域的 max-of-N 等待是噪声级联 30–70 ms 的来源（§13 构成分析）。
7. **光车道**——又一条 ConsecutiveExecutor；§17-18 判决它是 ~200/s 架构天花板的参与方之一。

## 5. `GenerationChunkHolder` 的并发就绪度审计

这是"动调度层是否安全"的核心证据（320 行全读）：

- futures 池：`AtomicReferenceArray` + `compareAndExchange` 创建（129–151 行）；完成走
  CAS+yield 循环（171–193 行）；降票时 failAndClear 全区间（153–169 行）。
- 状态抢占：`acquireStatusBump:219` —— `startedWork` CAS，输家拿赢家的 future。
- 引用计数：`generationRefCount` 原子，0→1 时挂 save 依赖（238–255 行）——**生成期间
  存盘会被 future 挡住**，任何并行化都必须保持这对 acquire/release 的配对。
- 满块替换：`replaceProtoChunk:94` 对每个 future 逐一 CAS，撞上并发的完成会直接抛错
  ——**它假设替换时没有并发的同状态完成**，这条假设在并行方案里要重新验证。
- 读视图契约：`WorldGenRegion.getChunk:111` 只允许读 `directDependencies` 表在该距离上
  保证的状态（`:115`），拿不到就生成崩溃报告（`:129` 起）。**阶段体的读集合 = 依赖表**，
  任何调度重写要么保持该表语义、要么显式重证。

**结论**：holder 层已经是"为并发探测而造"（Mojang 自己的选择）；单车道是**调度层**的
决定，不是数据层的约束。这正是 C2ME 与我们旧 offload 线共同的安全论证基础，26.1.2 源码
把它钉死了。

## 7. 贴近 GPU 逻辑的分层方案

原则：**不重写调度层，只拆串行化点**；GPU 管线（设备线程 2.85 ms/区块 + 双 replay
worker + 16 深队列）原样不动，让它喂得饱。每层独立开关、独立可回退，全部有先例实测。

**L1 半场下放**（吞吐主杠杆，预期恢复 §10-§12 时代的 ~1.8×）
- 内容：复活 `ChunkStepMixin` 的 `@WrapOperation`——把写半径 0 的同步体（SURFACE、
  CARVERS，26.1.2 落点即 `ChunkStep.apply:37` 的 `this.task.doWork(...)`）挪到后台池。
  簿记、JFR、完成链照旧留在车道上（旧实现的形态，已验证）。
- 安全论证：金字塔自己的语义（写半径 0 = 只写自己，§3 表）；holder CAS 兜底重复推进；
  PalettedContainer 的信号量本体保留、只绕 ThreadingDetector 的线程身份误报
  （旧 `ThreadingDetectorMixin` 原样可用，26.1.2 同名类）。
- 实测背书：+48% 噪声吞吐（§10 ④）；91 测试全绿 + 出生点干净完成的验收记录。

**L2 事件驱动续体**（延迟杠杆：噪声 p50 与"区块来得早"）
- 内容：两处小改。其一把 `runGenerationTask` 的 `thenRun` 重入队改成完成线程上的直接
  续体交接（保留取消检查）；其二把 `scheduleForExecution` 的整批 allOf 改为**每任务完成
  即让簿记车道可弹**（即旧 parallelSched 的语义，落在 `ChunkTaskDispatcherMixin`）。
- 实测背书：parallelSched p50 108→67–86 ms、lane busy 3% 证明它从来不是容量约束——
  预期收益全在延迟侧；cap 50 下端到端持平是已知结论，不要指望它提吞吐。
- 风险：直接续体打破"同一任务至多一个 continuation 在飞"的单车道假设——必须保留
  `runUntilWait` 的单续体结构（它的状态机本身就是为此造的，见 §2 步骤 3）。

**L3 FEATURES 专用线程**（写半径 1 的正解）
- 内容：写半径 1 的 FEATURES 不下放并行，改挂专用单线程执行器（旧
  `featuresDedicated()` 路线），其余阶段照旧。
- 实测背书：2:07 纪录即在此形态（§16）；写区 gate 轮询比串行还慢（§17 #3）——
  FlowSched 的 LockToken 路线同理属于"并行收益买不回锁开销"的范畴，除非 FEATURES 体
  量大到值得（见 §8 税单）。
- 税单警告：C2ME 的 fixes-worlding 群证明 FEATURES 并行会唤醒结构生成器里的共享可变
  状态；单线程方案天然免单。

**L4 tick/主线程耦合**（最后动，收益中风险高）
- 内容：C2ME 的 mid_tick 路线（tick 中段泵区块任务）或 FULL 体批处理。落点：
  `ServerChunkCache.runDistanceManagerUpdates` 与 `ChunkStatusTasks.full:179` 的
  `supplyAsync(..., mainThreadExecutor)`。
- 为什么最后：主线程是票务/满块晋升的串行一致性锚（§1 表、§2 步骤 6），动它要重新
  证明 `updateFutures`/`onFullChunkStatusChange` 的顺序语义；且入场泵在请求路径上
  已有即时泵送（`getChunkFutureInternal:246`），只堵了纯票驱动的一截。

**与 GPU 管线的融合点**（"贴近已有逻辑"的真正含义）
- L1–L3 都不碰 GPU 管线，它们的作用是**把波纹推进得更快、让 NOISE 的到达更密集**，
  从而把 GpuWorldgenService 的 16 深队列从"常空"喂到"常满"——设备线程 busy 从 15–25%
  向上走，2.85 ms 的服务能力才被兑现。
- 唯一的直接融合候选：波纹天然造成**NOISE 同伴批**（一圈区块同时到 NOISE）——
  M4 时代否决过的"批处理"（§三）在调度重写后值得用 dwell 视角重估一次，但那是后话。
- **26.3 前瞻**：调度层类在 26.3 全部存活（FastNoise 的 mixin 目标即同族类），L1–L3 的
  投资跨版本保值；而 GPU 密度卸载的价值在 26.3 缩水一个量级（§14：vanilla 阶段体只剩
  11.5 ms）。**换句话说：调度层是 26.3 时代的资产，GPU 密度是 26.1 基本盘的资产**——
  两者的组合恰恰是本 mod 的完整故事。

## 8. 风险与不变量清单（实现时的对照表）

1. **读视图契约**：阶段体只能读依赖表保证的状态（§5）；下放体不改变读集合。
2. **save 同步**：`generationSaveSyncFuture` 的 acquire/release 配对（§5）——下放不碰
