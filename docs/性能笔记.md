# 性能笔记

这份文档记录测量结果和由它们逼出来的决定。README 描述这个 mod 是什么；这里记录它为什么是现在这样。

所有数字来自 RTX 3080 / 12 逻辑核，`ChunkPassProfileTest` 和真实世界的 `runClient` 运行。

## 一、一个区块的时间去哪了

设备路径下每区块约 **6.7 ms**：

| 阶段 | 耗时 |
|---|---|
| marker 角点表（每个程序一次 launch） | 2.1 ms |
| 逐方块 pass（插值 + 标记之上的 DAG） | 0.9 ms |
| 材质规则（含水层 + 矿脉，CPU） | 2.2 ms |
| 其余（宿主侧、分配） | ~1.5 ms |

真实世界里这条路能跑 **约 64 区块/s**，而 GPU 自己那份工作量的容量是 **149 区块/s**。
**设备不是瓶颈。** 另一半证据：把 SURFACE + CARVERS 整个从串行 dispatcher 上拿掉之后
（每区块 14.5 → 6.84 ms，忙碌度 74% → 34%，上限 69 → 146 区块/s），**吞吐没变**。
dispatcher 也不是瓶颈。真正的限速在两者更上游，尚未查明。

## 二、这个 mod 到底有没有用

有三组测量，可信度递增。

**同一区块、同一机器、单线程对照**（这一组最可信）：

| | 成本 |
|---|---|
| vanilla 的 NOISE 阶段 | **18.1 ms 单核 CPU** |
| 这个 mod 的等价密度 | **1.97 ms GPU** |
| 这个 mod 整块（含材质规则） | 6.7 ms |

**端到端**：vanilla 约 **22.5 区块/s**，带 mod **40–64 区块/s**（约 2×）。

**代价**：单区块延迟变差。noise 的 future 要 ~105 ms 才完成（6.7 ms GPU + 排队），vanilla 是 25.5 ms。
**一个串行 GPU 加队列 ≠ 一个并行线程池** —— 每秒更多区块，但每个来得更晚。

收益来自**让出 CPU 核**，不是让出 dispatcher。这是它和"把某阶段从 dispatcher 挪到别的 CPU 线程"
的本质区别。

## 三、批处理为什么没做

设计文档的前提是"一个区块的角点表是延迟受限的"（6450 点 × 450 步串行链 ≈ 5% 占用率），
所以多个区块合一次 launch 应该几乎白赚。测出来不是：

| 每批区块数 | 总计 | 每区块 |
|---|---|---|
| 1 | 1.55 ms | 1.55 ms |
| 4 | 4.00 ms | 1.00 ms |
| 8 | 7.77 ms | 0.97 ms |
| 16 | 13.71 ms | 0.86 ms |

16 倍线程只换来 1.8×，说明 kernel 并不是单纯在等占用率。而 scratch 与批次线性增长
（`点数 × 指令数 × 8`），8 个区块要 200 MB 换 0.7 ms/区块 —— 而 GPU 还有 2× 余量，根本显不出来。

**记录而未实施。** 数字在 `ChunkPassProfileTest` 里，任何人可复现。

## 四、M4 逐项状态

规划把 M4 定义为"批处理 + pinned 双缓冲 + halo 合并"，验收是"≥8 chunk 批摊销；P95 时延报告"。

| 项 | 状态 |
|---|---|
| **批处理** | **测量后否掉**，见上 |
| **pinned 双缓冲** | **未开工**。收益是 D2H：每区块 3 次 786 KB，可页内存 9.7 GB/s ≈ 0.24 ms（总共 6.7 ms）。翻倍也只省不到 2% |
| **halo 合并** | **未开工，且单独做没意义**。一个区块的角点网格是 5×5 列，最外一行一列属于邻居、被算了两次 —— 25 列里 9 列重复。去重能省约 1/3 的角点工作量，但**前提是多个区块同时在飞**，那就是已经否掉的批处理 |
| **≥8 chunk 批摊销** | 未达成，是上面那个决定，不是遗漏 |
| **P95 时延报告** | **已闭环（仪器）**。`-Ptiming` 现在保留逐区块样本而不是只累加：混入侧每 256 个区块报告噪声阶段时延的 p50/p95/p99/max，服务线程每窗口报告服务时间的 p50/p95。无头专用服务器冒烟已验证代码路径（出生点区块走接管、0 异常、0 回退），窗口数字待下一次带玩家的 runClient 记录 |

**M4 至此没有未决项。**

## 五、已做的那部分

每区块 16.2 ms → 6.7 ms，吞吐 40 → 64 区块/s，来自四处：

1. **每个程序一次 launch 而不是每个 marker 一次**（角点表合并）
2. **逐方块 pass 从宿主搬到设备** —— 原本是 CPU 上 7.7 ms 解释 DAG + 3.5 ms 插值
3. **dispatcher 不再被阻塞** —— Mixin 返回未完成的 future
4. **宿主暂存缓冲复用** —— 每次新分配 786 KB 原生内存的首次触碰缺页，比它要搬运的那次拷贝还贵

第 2 条是最容易判断错的一条：只搬插值（不回传整块）是**负优化**，因为把 3.9 MB 的原生缓冲
变成 Java 数组只有 4 GB/s，吃掉了大部分收益。设备连 DAG 一起算、每方块只回传一个 double 才对。

## 六、拆线之后：P1 实测（2026-10-05）

**基准协议**（定下来，以后对比都用它）：种子固定 `123`，视距拉到 32，传送 `(1000, 1000)` 后站定，
看传送后的窗口（约 4,700 个区块）。拆线前的预测是 service 11.6→5.3 ms、busy 79%→约 35%、吞吐不动，
三项全部命中：

| | 拆线前 | 拆线后 |
|---|---|---|
| service | 11.6 ms | **5.5–6.5 ms**（中位 5.8） |
| 设备线程 busy | 79–84% | **均值 43%**（渲染抢卡窗口 50–77%） |
| 吞吐 | ~57–68 /s | **均值 66 /s**（52.9–89.3） |
| 分段 ms | density 3.0 / veins 2.3 / rules 4.1 / replay 2.2 | density 3.7 / veins 2.4 / rules 4.9 / replay 1.8 |
| 噪声阶段 p50 | ~105 ms | **59 ms**（中位 56） |

- **视距 32（一次 ~4,225 个区块的需求）也没能超过 ~66/s** —— 上限钉死在上游。设备线程容量
  ~180/s、规则 worker ~149/s（6.7 ms/区块），两者 busy 都不到一半。**上游是唯一绑定约束，
  P2 是唯一的吞吐杠杆。**
- **Little 定律给出在飞 ≈ 3.9 ≈ 4 个区块**（66/s × 59 ms），与 `maxChunksInExecution=4` 惊人吻合；
  但拆线前同一算法给出 7.1（68 × 105 ms）并不吻合。说明那个节流器到底数什么仍未证实 ——
  这是假设不是结论，P2 用 `getDebugStatus()` 插桩裁决。
- p95 ~171–186 ms：尾部是排队不是服务。传送后 4,000+ 区块同时拿到票，队列深度直接进尾延迟。
- 渲染抢卡首次拿到时序证据：个别窗口设备 pass 时间翻倍（density 5.5 + veins 6.0 ms，busy 77%）。
- beardifier 让路 769/9,600 ≈ 8%；全程 0 异常 0 回退。
- rules 段从 4.1 涨到 4.9 ms：跨线程/cache 代价，或测量口径变化（现在含 setChunk）。量级没变，记录不解释。

**下一个实验**：同协议跑一次 vanilla 基线（不加 `-Pterracuda.gpu`），拿种子 123 的同地形 A/B；
之后 P2 动上游。若无头复现，Chunky 强制加载可以去掉"玩家/视距"这个变量（用户提的，待试）。

## 七、上限的机制：源码确认，仪器补齐（2026-10-05）

读 `ThrottlingChunkTaskDispatcher` / `DistanceManager` 的反编译源码，把此前所有推断变成了机制：

- 节流器的"在飞"槽位**只在区块到达 entity-ticking（完全加载）时释放**——`runAllUpdates` 把
  `release` 挂在 `getEntityTickingChunkFuture()` 上。`maxChunksInExecution=4` 的真实语义是
  **最多 4 个区块同时走在"拿到玩家票 → 完全加载"的路上**。
- 于是加载吞吐 = 4 ÷ 每区块全程耗时。以 `-Ptiming` 量到的 ~62 ms dwell 计算：**4/0.062 ≈ 65/s**，
  与实测上限严丝合缝；Little 定律的 3.9 ≈ 4 从此有源码背书。
- 完整的墙模型：**节流器 ~65/s 与串行 dispatcher ~69/s（`-Poffload` 时代实测 14.5 ms/区块）几乎叠在一起**。
  这解释了为什么单动任何一个都不涨——`-Poffload` 单动 dispatcher（51→55），P1 单动设备线程（~66 不变）。
  要越过 ~65–69/s，两件得一起动。

仪器（`e4fba44`）：

- 噪声阶段完成计数改挂在 `fillFromNoise` 的 **RETURN** 上，**vanilla 模式同样计数**——同协议的 vanilla
  基线现在产出与接管模式同源的窗口曲线（含尾流）。第一次掐表对比作废：退出时刻 ≠ 加载完成时刻（用户纠正），
  唯一稳健的推论是 vanilla ≥ ~57/s（全部需求在 ≤85 s 内完成），和 mod 同在 ~60/s 带。
- 每窗口附带节流器自己的 `getDebugStatus()`：in-flight 集合 + sleeping 标志，贴着它管的速度印出来。
- 实验开关：`-Pinflight=N`（默认关）把 4 抬到 N，触发时打一行日志。

**待跑的实验矩阵**（协议不变：种子 123、视距 32、传送 (1000, 1000)）：

1. `runClient -Ptiming`（纯 vanilla + 计数）→ 基线曲线，含尾流形状；
2. `runClient -Ptakeover -Ptiming` → mod 曲线，与 ① 同源对比；
3. `runClient -Ptakeover -Ptiming -Pinflight=8` → 节流器放开后撞到哪（预测：串行 dispatcher 的 ~69/s）；
4. 若 ③ 印证 dispatcher 是下一道墙，复活 `-Poffload` 两件一起动。

另有未解：modded 会话的 1.7/s × 75 s 尾流（最后 125 个区块）——成因待 ① 的 vanilla 曲线与节流器
窗口状态裁决。

## 八、实验矩阵的判决：节流器不是墙，串行 dispatcher 才是（2026-10-05）

三场同协议运行（种子 123、视距 32、传送 (1000,1000)，每场删世界重建）：

| | ① vanilla | ② takeover | ③ takeover + `-Pinflight=8` |
|---|---|---|---|
| 噪声阶段吞吐 | **71.8/s**（5,888 个 / 82.0 s，计数器全程有效） | ~62/s（GPU 窗口；计数器有盲区，见下） | ~67/s（GPU 窗口） |
| 节流器在飞 | **全程钉在 4** | 钉在 4 | **钉在 8**（开关生效） |
| 噪声阶段 p50 | — | ~57 ms | **~101 ms，翻倍** |
| 尾流 | 无（75/s 干净收尾） | 一个 12.2/s 慢窗 | 不明显 |

**判决：节流器从 4 抬到 8，在飞翻倍、吞吐不动（62→67，同带）、dwell 从 ~64ms 涨到 ~120ms、
p50 延迟翻倍。** 这是"流水线内有一个串行资源在排队"的标准特征——in-flight 只是替它维持更深的队列。
串行资源的单区块成本 ≈ 1/65s ≈ **15.4 ms，与 `-Poffload` 时代实测的串行 dispatcher
（14.5 ms/区块 → ~69/s）吻合**。三场全落在 ~62–72/s 带上，正是这道墙。

- **第七节的墙模型要修正**：不是"两道墙几乎叠着"，而是**串行 dispatcher 在前、节流器弹性跟随**。
  节流器全程钉满是 dispatcher 慢的症状，不是原因；抬它只买到更深的队列和更差的延迟（③）。
- **① vs ② 的 A/B**：vanilla 71.8/s 与 takeover ~67/s（62/0.92 折算含让路区块）同带——
  此负载形态下 mod 端到端无增量，因为 dispatcher 压着两边。不是 mod 没用，是 dispatcher 不放行。
- ②复现了慢尾窗（12.2/s），①没有——成因仍未定，已不是主线索。
- **计数器接管盲区（同日修复，`a06a5d8`）**：HEAD 取消路径不经过 vanilla 的 RETURN 指令，
  接管区块此前没被计数（②③的 "noise stage" 线只数到让路的 ~10%）；现在接管路径挂在自己的 future 上，
  重入有 `IN_VANILLA` 守卫防双计。①的数据不受影响，全程有效。

**下一步（顺序修正后的 P2）**：复活 `-Poffload`——把半径 0 的阶段从串行 dispatcher 下放
（安全论证存 2026-10-04 工作区日志），预测天花板从 ~69/s 抬到 ~146/s（该次实测 dispatcher
下放后剩 6.84 ms/区块）；dispatcher 放行之后，节流器才会重新成为需要动的第二道墙。

## 十、墙的接力赛跑完了：④⑤ 与无头 A/B（2026-10-06）

### ④⑤（客户端，协议不变：种子 123、视距 32、传送 (1000,1000)）

| | ② 基线 | ④ +offload | ⑤ +offload +inflight=8 |
|---|---|---|---|
| 噪声阶段吞吐 | ~67/s | **~99/s（+48%）** | **~113/s（再 +14%）** |
| GPU busy | 43% | 55%（峰值 85%） | **74%（峰值 99.9%）** |
| 全程墙钟 | — | **57 s / 5,504 区块** | — |

预测全中：dispatcher 放行后节流器在 ④ 重新钉 4，⑤ 抬到 8 又换来一段——**然后轮到 GPU 线程**。

### 无头 A/B（Chunky 1.5.4 + RCON 驱动，同种子同区域同条件）

Chunky 装在 `run/mods`；[`benchmark/chunky-rcon.ps1`](../benchmark/chunky-rcon.ps1) 经 RCON 驱动无头
服务器（协议：`server.properties` 开 RCON、`level-seed=123`、删 `run/world`，起服后
`chunky shape square / center 0 0 / radius 1200 / start`），22,801 个区块两边都跑到 100%：

| | vanilla（`-Ptiming`） | mod（`-Ptakeover -Ptiming -Poffload`） | 差 |
|---|---|---|---|
| Chunky 总耗时 | **5:10** | **2:55** | **1.77×** |
| Chunky 稳态速率 | ~78–87 cps | ~140–149 cps | ~1.7× |
| 噪声阶段中位 | 79.1/s | 140.6/s | **1.78×** |
| 绑定约束 | 串行 dispatcher | **GPU 线程**（busy 均值 87.6%，86/162 窗口 >90%） | — |

- **这就是受控的"约 2×"：1.77×**，同地形、同区域、无头同条件，不再是跨会话的推断。
- vanilla 无头跑里玩家节流器全程空转（窗口行无 tickets 段）——Chunky 的票不经过它，这场量的是
  dispatcher 墙本身（~79/s，略高于客户端场景的 ~69，地形/口径差）。
- mod 侧 GPU 线程观测服务 ≈7 ms（含被 worker 顶住的 handoff 等待），容量 ~142/s；worker
  （rules+replay ≈6.7 ms）容量 ~149/s 同时接近饱和——两线程联合上限 ~145/s，与稳态吻合。
- 延迟代价：p50 130–400 ms（饱和排队）——无头无感，有玩家时就是"区块来得晚"。
- 未解小事一件：接管场里节流器在飞位置出现在 [75,94] 等远离出生点处（来源未明；不影响测量，
  节流器只占 ≤4 个无关槽位）。

**P2 闭环**：四道墙按序测到并拆除——串行 dispatcher（69）→ 玩家节流器（4/dwell）→ GPU 线程（~142/s），
受控 A/B 落袋。**GPU 线程成为系统瓶颈意味着 mod 的下一步投入直接兑现**：按既有分析，先做多流 +
event 替代 `cuCtxSynchronize`（三段设备 pass 重叠，服务 5.5→~3.5 ms，容量翻向 ~285/s），
worker 到时再扩。Chunky+RCON 协议从此可复现任何一场。

## 十一、多流：重叠是真的，但墙原来在 worker（2026-10-06）

三段提交-三段等待（`70209d4`）+ 回传暂存页锁定（`f903ea4`），同协议四场：

| | 基线（串行） | 流，未 pin | 流+pin 第①跑 | 流+pin 第②跑 |
|---|---|---|---|---|
| Chunky 总耗时 | 2:55 | 3:02 | 3:17 | **2:44** |
| 设备段（density+veins） | 3.9 ms | 4.1 ms | 3.5 ms | **2.9 ms** |
| rules / replay | 5.1 / 2.3 | 5.3 / 2.3 | 6.2 / 2.4 | **4.8 / 2.1** |
| worker 容量 | 135/s | 130/s | 116/s | **145/s** |
| 噪声阶段中位 | 140.6/s | — | 125.6/s | **150.8/s** |

- **第一课（未 pin 的流）**：`cuMemcpyAsync` 的 D2H 对 **pageable** 宿存会阻塞调用线程——驱动无法推迟
  写入一块宿主可能改用的内存，规划文档 §4.3 写过这条，实现时忘了。每次提交都终结于一次 D2H，
  所以每次提交都在等自己整条流跑完，三个程序照样串行（分段 d 3.7 + v 0.4 一眼看穿）。
  **页锁定不是优化，是 overlap 的前提**；M4 时代"pinned 不值"的判决属于旧串行管线，理由已变。
- **第二课（第①跑的假回归）**：rules 6.2 ms、3:17——同配置复跑得 **4.8 ms、2:44**。回归是机器状态
  方差，不是代码。**本机单场端到端数字的带宽 ±18%（3:17 vs 2:44 同配置）**：跨场比较必须看分段
  （分段是机制性的、可复现），端到端要复跑。
- **第三课（归因修正）**：第十节把"GPU 线程是瓶颈"归因过头了——busy 87.6% 里含 put 等待，
  设备占用其实只有 3.9/7.05 ≈ 55%。**无头场景的绑定约束一直是 rules worker**（基线 7.4 ms → 135/s，
  与观测 124–130 吻合）；客户端 ⑤ 的"GPU busy 74%"来自渲染抢卡 + 节流 dwell，不是设备饱和。
- **判决**：设备墙 3.9 → **2.9 ms**（overlap 机制性生效），端到端 2:55 → **2:44**（+6.7%，
  受 worker 压着）；噪声中位 150.8/s 创新高。**下一道墙毫无悬念：rules worker ~7 ms（140–145/s）**
  ——扩 worker（2 线程、每 worker 一份解释器，P1 设计时的既有方案），之后才是 dispatcher 剩余（~196/s）。

## 十二、worker 扩容：清了墙，墙在别处（2026-10-06，`3dff230`）

每 worker 一套解释器（共享不可变的 `DensityProgram`），`-PrulesWorkers`（默认 2）。同协议：

| | 1 worker（十一节②跑） | 2 workers |
|---|---|---|
| Chunky 总耗时 | 2:44 | **2:43（平）** |
| 噪声阶段中位 | 150.8/s | 155.4/s |
| **噪声阶段 p50 延迟** | 249 ms | **118 ms（减半）** |
| GPU busy | 87% | **67%** |
| rules / replay（跨 worker 累计） | 4.8 / 2.1 | 7.1 / 3.2（每 worker 墙钟 ~5.1 ms） |

- **worker 墙确实存在也确实被拆了**——p50 延迟减半（队列双速排空）+ GPU busy 从 87% 降到 67%
  （设备线程不再等 worker）就是机制性证据。**但吞吐纹丝不动**。
- **归因的归因修正（第三课的修正）**：十一节判"下一道墙是 worker"又对了一半——worker 145/s 与
  dispatcher 剩余 ~146/s **恰好数值相等**，两个天花板叠着，拆掉 worker 那道后另一道原样顶上。
  单场数据分不出两道数值相同的墙；只有拆掉其中一道（本次）才暴露另一道。
  **教训入账：当天花板 A 的容量 ≈ 天花板 B 的容量时，"A 是瓶颈"的结论未经拆 A 无法证实。**
- **现在的墙**：串行 dispatcher 的剩余阶段——FEATURES 23.2%（写入半径 1，刻意串行）+ structure_starts
  5.7% + light/spawn/full 微量 ≈ ~6.8 ms/区块 → **~146/s 上限**，与 GPU 线程速率 144.5/s 和噪声
  中位 155.4/s 同带吻合。
- **当前端到端**：2:43（mod）vs 5:10（vanilla）= **1.9×**；延迟减半是玩家可感的实际收益。
- **下一杠杆的代价表**：FEATURES 是"任意 Java"（几百个 `Feature` 子类 + mod 会加），C2ME 用整个
  FlowSched 重写 + fixes-* 线程群才吃下它——那是把整个 vanilla 调度栈换掉的工程量，
  本 mod 已用 `-Poffload` 拿到了半径 0 阶段的便宜，FEATURES 的串行留在原地是刻意的。
  **mod 侧已无低垂果实**：设备 3.5 ms（容量 ~285/s）、worker 对 ~5.1 ms 墙钟（~190–390/s）、
  全都远高于 dispatcher 的 146/s——接下来要么动 FEATURES（大工程），要么接受 ~155/s 的稳态。

## 十四、对照测量：zFastNoise（26.3，2026-10-12）

[zFastNoise]（MPL-2.0，Fabric，源码 `D:\Project\FastNoise`）是 26.3 上**同契约**的噪声
优化 mod——也做 parity 测试。技术路线互补：它**不动密度数学**（直接用 26.3 的
`PooledSampleBuffer.getFilledBuffer` 区域采样 API，即版本策略里预判的那个干净注入点），
优化的是**填充半场**——FastChunkSection 空段落/调色板技巧、取消区块锁与簿记、

用它的 perf 工具实测（JMH-in-server，`terrain` 基准 = 26.3 的 TERRAIN 阶段整段，
33×33 区域/次，单线程，种子 123，同架自比 vanilla/mod，同机）：

| MC 26.3 overworld | ms/op（1089 区块，avgt×5） | ms/区块 |
|---|---|---|
| vanilla | 12,549 ± 1,622 | **11.53** |
| zfastnoise | 8,572 ± 888 | **7.88** |
| **阶段体比值** | — | **1.46×** |

判读与边界：

1. **跨版本绝对数不可比**：26.3 的 float 化噪声栈让 vanilla 阶段体单线程只要 11.5 ms

2. **口径不同，比值各归各**：它测的是隔离阶段体（无 dispatcher、无管线），我们的 1.11×

4. 许可注意：MPL-2.0（文件级 copyleft）——可读可参考，一行不抄，与 C2ME 红线同一纪律。

## 十五、L1+L3 复活：调度层扩展的第一阶段落地（2026-10-13）

按第十四节报告的路线，从 `backup/full-pipeline` 平移了两道实测杠杆，作为**默认关、
`-Poffload` 开启的可选性能包**重新进入主线（91 测试全绿，jar 构建通过）：

- **L1 半场下放**（`ChunkStepMixin`）：写半径 0 的阶段体（NOISE/SURFACE/CARVERS）挪到
  共享后台池，簿记/JFR/完成链留在 dispatcher 上照 vanilla 走。**判据收窄回 `radius == 0`**
  ——不带旧线 75fb895 的"全阶段除 LIGHT"扩展：那次实测端到端持平，却把结构生成器体
  推上并发路径（C2ME 税单点名的风险面，报告 §8.7）。
- **L3 FEATURES 专用线程**：写半径 1 的 FEATURES 挂单线程执行器（无串行回退——回退正是
  当年死锁的成因）。**FeaturesGate 未移植**（旧线里的死代码，gate 轮询实测比单线程慢）。
- `ThreadingDetectorMixin` 原样平移：信号量保留、线程身份误报绕过，仅 offload 开启时生效。

## 十六、逐层归因仪表：dwell 的解剖表（2026-10-13）

新仪器：`LayerTiming` + `ChunkGenerationTaskMixin`（`-Ptiming` 门控，对任何形态生效——
vanilla 也能测）。三把尺，全部按状态聚合成 10 秒窗口（p50/p95/mean）：

- **wall**：某层首步 → 任务续体观察到该层全排空（同步层=体的时间；会停泊的层含一跳重入队）；
- **requeue**：层停泊后"最后一个 future 完成 → 续体再上车道"的往返——调度层目标（L2）的直接测量；
- **dwell**：任务首步 → claim 释放（含取消）。

### 判读

1. **vanilla 的 dwell 大头是 FULL**（主线程执行器 + 晋升积压，p95 冲到秒级）——L4 判断
   的对象在 vanilla 侧成立；但 **offload 态下它塌缩到 4.5 ms**：管线畅通后晋升不再堆积，
   **L4 的无头收益空间在 offload 形态下基本不存在**（这是 L4 最重要的立项否决证据）。
2. **offload 态的每区块停留大头显形为 FEATURES 层：p50 85 ms**——专用单线程的排队+服务
   （vanilla 里它只是 2.4 ms 同步体）。§15 报告 §7 L3 的"税单"预言量化落地：
   **下一杠杆的靶心是 FEATURES 的 85 ms**——第二线程需要写区 gate（旧实测：轮询吃掉收益），
   或者直接 profile `applyBiomeDecoration` 砍服务时间。
3. **NOISE 层 85 ms 中 GPU 服务只有 2.85 ms**——其余是队列等待（p95 347 ms 深尾）；
   修 FEATURES 也会间接收窄 NOISE 的队尾（在飞变浅）。
4. **EMPTY/STARTS 的波纹扇出**：每任务 17×17 数百步、每窗口 25 万+ 步——墙≈0，但它是
   调度开销的量纲证据（lane 的 noteStep 调用频率上限由此而来）。
5. 仪表运行本身在方差带内（2:40 vs 2:17，+17.6% < ±18% 单场带宽）；归因比例取自场内
   稳态窗口，机制性结论不受绝对值波动影响。仪器校准遵循既定教训：它看见了它声称测量的
   改变（L1+L3 前后 dwell 4× 差异即已知量）。

## 十七、靶心的解剖：FEATURES 判死，GPU 队列给了个延迟旋钮（2026-10-13）

§16 把 offload 态每区块停留的大头标成 FEATURES 层 85 ms。给仪器加了两把尺——
下放体的 **queue**（提交→开跑）与 **svc**（开跑→阶段 future 完成），两个下放分支
（半径 0 池、FEATURES 专用线程）都套了探针；另对 features 线程做了 300 样本的栈采样。

### FEATURES 85 ms 的解剖：判死

| | p50 | mean |
|---|---|---|
| queue（专用线程排队） | **70.6 ms** | 77.2 |
| svc（体本身） | **3.5 ms** | 4.5 |
| 栈采样（300 个） | 179 RUNNABLE / 121 停泊 | — |

- **svc 只有 4.5 ms，主体是矿石放置**（栈采样：OreFeature.place+doPlace ~38%、
  ProtoChunk/PalettedContainer 块读取 ~22%、getBiome ~10%）——vanilla 逻辑，逐位契约
  不许动，而且太小不值得动。
- **queue 70 ms 是波纹串行**：一圈 ~12 个相邻区块同时到 FEATURES，单线程按 4.5 ms/个
  排水（λ·W 自洽）。并行化需要邻接仲裁：旧写区 gate 实测轮询吃掉收益；静态着色不可行——
  任意两色都能相邻，不同色并发 = 邻居读到半改状态 = **地形偏离 vanilla，违反契约前提**。
  **单线程就是 FEATURES 的正确形状，此杠杆对吞吐判死。**

### 真正的大头是 NOISE 的 svc：GPU 管线队列（给了个旋钮）

noise svc p50 146 / mean 189 ms——GPU 服务本身只有 2.85 ms，其余是管线等待
（REPLAY_CAPACITY=16 深的队列 ≈ 16/166cps ≈ 96 ms，恰好吻合）。把容量旗标化
（`-PreplayCapacity`，默认仍 16）做扫描：

| | capacity 16 | capacity 8 | 判 |
|---|---|---|---|
| noise svc p50/mean | 146 / 189 ms | **105 / 141 ms** | **−28% 延迟** |
| noise wall p50 | 90.3 | **58.9** | −35% |
| task dwell p50/mean | 182–212 / 213–249 | **175 / 217** | 轻微改善 |
| GPU busy（尾部窗口） | ~72% | **81%** | 无耦合悬崖 |
| Chunky 端到端（带探针） | 2:32–2:40 | **2:17** | 持平偏好 |
| features queue | 73.9 ms | 70.2 | 无关此旋钮 |

**判决**：8 容量砍掉 28% 噪声延迟且端到端不亏、GPU busy 上升而非塌陷（4 容量时代的
37% 耦合损失没有出现——悬崖在 4 与 8 之间靠 4 那侧）。**默认保守留 16**（时代验证过的
抖动吸收器，高负载服务器有玩家时更稳），8 是"延迟调优档"，旗标出货。

### 本节的路线判决

offload 形态的剩余停留 = noise svc（105–146）+ features queue（~74，正确性约束）+
light/init_light（~31）——全部是队列/正确性约束，**无头协议下管线已贴近其结构上限**。
下一步的真正分岔：26.3 适配重估（float 栈把整个账本缩小一个量级），或转向客户端场景
（节流器 4÷dwell 的世界，queue 数据结构完全不同）。

## 十八、26.3 立项重估：噪声栈实读与移植账本（2026-10-13）

完整评估见 [`docs/26.3噪声栈移植评估.md`](26.3噪声栈移植评估.md)（26.3 merged-deobf jar
反编译精读）。决策相关的数字与判决：

- **26.3 密度栈全 float + `sampleVolume(DensityBuffer, DensityVolume)` 是接口自带的一等
  公民**——26.1 时代预判的"干净一个量级的注入点"由官方落地；GPU 实现只需替换顶层
  sampler 的一个方法。float 化对 GPU 双重利好（parity 同型 + 摆脱消费卡的 double 包袱）。
- **管线同构**（NOISE→TERRAIN，`ChunkStatusTask.doWork` 打点同名、TERRAIN 体仍
  supplyAsync 逃逸）——调度层资产近乎逐字平移。
- **价值缩水**：vanilla 阶段体 11.53 ms（zFastNoise JMH 同机实测）对 26.1 的 ~40 ms；
  zFastNoise 已占 CPU 侧 1.46×（7.88 ms）；GPU 密度路径的净空间 ~7-9 ms/区块，
  **是 26.1 时代的三分之一**。
- **判决**：值得做、按"26.1 基本盘"优先级排；立项首周做 parity 原语 float 化（测试
  架构全复用），随后平移调度层先测 26.3 vanilla 的 dwell 归因——dispatcher 墙若仍在，
  26.3 首发卖点与 26.1 相同：offload 包，而非 GPU。

## 十九、G1 波纹批处理：机制成立、判决为负（2026-10-13）

第二代管线的第一杠杆落地实测。机制（`-Pbatch`，默认关）：设备线程把排队中的填充作业
排空成波（上限 16），corner 表一次启动、blocks 逐区块（偏移指针读各自的表切片）、
回传逐区块、每程序每波一次流同步。波 parity 由新增的逐位测试背书（8 区块波 vs 逐区块
solo，0/786432 差异）——期间修掉一个真 bug：FFM `MemorySegment.copy` 的段偏移是**字节
不是元素**（旧代码的 `0L` 掩盖了这一点；元素偏移会让 chunk 1 从 chunk 0 的数据区内部

### 机制归因：批处理-屏障 vs 流水线

逐区块模式是一条**跨区块流水线**：区块 N 在 replay worker 手里时，N+1 已经在设备上，
两半跨区块重叠。波模式是**批处理-屏障**：整波设备完成（awaitWave）后才整波移交 replay
——波内最先进的区块要等最慢的兄弟，然后整波挤进 replay 队列。启动摊薄是真的
（14.2×），但换来的是把流水线的重叠拆成两段串行。dwell 被 cap 50 的 Little 定律钉死，
重排只改变停留的**构成**——noise 份额翻倍，其余阶段缩小，端到端纹丝不动。
**与 §15 L2 节同构的教训第三次出现：cap 下重排延迟分布不产生吞吐。**

### 判决与出路

- `-Pbatch` **默认关保留**（parity 已证、机制干净、是后续精炼的基体）。
- 记录为推断的精炼假设：**流水线化波**——波设备提交后不等整波，按每区块流事件逐个移交
  replay（设备线程异步排水）。它保留启动摊薄又拆除屏障；但这是更大的重构，先按住。
- **§17 的结论被第三次验证：cap 下的延迟重排全是死路，只有改变停留总量的结构杠杆有效
  ——那就是 G2（规则上 GPU，把设备+replay 两段熔成一段设备阶段，消灭接力本身）。**

## 二十四、保存退出卡死：一次事件时序的教训（2026-10-14）

**现象**：客户端跑图数分钟后"保存并退出"，永久停在"正在保存"，强杀才退（exit
0xCFFFFFFF，无 crash report）。日志死在 `Saving worlds` 之后，逐层 `Saving chunks`
一行未出。

**机制**（反编译 + 日志 + 无头复现三重钉死）：`MinecraftServer.stopServer()` 在
"Saving worlds" 与逐层保存之间有一段排空循环——反复 tick 区块源直到
`chunkMap.hasWork()` 对所有层为 false。NeoForge 的 `ServerStoppingEvent` 在这段
**排空之前**触发，而我们的 `releaseAll()` 挂在它上面：close = 置 closed + interrupt
GPU 线程 → 线程走 closeQuietly 释放 CUDA 上下文并退出 → **fillJobs 队列里尚存的
FillJob 永远不跑** → 那些区块的 NOISE future 既不完成也不异常 → 任务永久 park →
hasWork() 永 true → 排空死转。飞行途中退出必有在飞区块，故必卡。

**为什么基准从未发现**：三次基准的 RCON `stop` 都发在预生成**完成之后**——没有
在飞工作，排空瞬间走完。"带在飞区块退出"这条路径在无头协议里从未被走过。

**无头复现**（修前）：chunky 起飞 45 秒（cap 50、fillJobs 队列 ~10-30 块积压）
发 stop → 日志止于 `Saving worlds`（23:49:44.635），之后只有 LayerTiming 守护
报告，进程永不退，强杀收场。

**修复**：`releaseAll()` 从 ServerStoppingEvent 挪到 **ServerStoppedEvent**
（stopServer 全部完成后、排空已走完，关闭不再可能搁浅任何 job）。replay 线程
本就排空后退出，语义不变。97/97 绿。

**无头验证**（修后，同一协议）：stop（00:19:46.888）→ `Saving worlds` →
**13ms 内**走完排空 → 逐层 Saving chunks 正常 → 进程 exit 0。

**教训**：生命周期事件的"先后"是功能正确性的一部分；排空循环的终止条件
（hasWork）覆盖了我们管线的输出，那么任何让它断供的钩子都会把它变成死循环。

- 剩余可省的 CPU：replay 1.4 核（writeChunk 写方块，天然成本）、Worker-Main 2.0 核
  （SURFACE/CARVERS 体+调度）、GC 0.33 核（分配瘦身）。全榨干的理论上限 ~220-240
  cps（+30%），工程量与收益不成比例——**吞吐线在本机正式结题：2.15-2.3×，
  与 C2ME 同机打平，墙是 CPU 容量**。若换核更多的机器，GPU 省 CPU 的比例优势
  才会显现（记录，不在本机范围）。

## 二十六、饥饿实验：把 CPU 少给一半，谁先倒下（2026-10-15）

问题：GPU 路线省下的 CPU 是真实的吗？方法：`ProcessorAffinity=0x3F`（6 逻辑核
≈3 物理核）同协议（cap 50、种子 123）对打；先补 C2ME 满血线程画像（此前从未采过）。

| | 满血（12 逻辑） | 饥饿（0x3F） | 每区块 CPU（满血实测） |
|---|---|---|---|
| 我们（offload） | 2:04 / 183.9 | **3:16 / 116.4（−37%）** | 527%/183.9 = **0.0287 核·s** |
| C2ME | 2:09 / 176.4 | **2:44 / 139.1（−21%）** | 364%/176.4 = **0.0206 核·s** |

### 判决：满血打平的原因与推测相反

- **C2ME 每区块瘦 31%**（0.0206 vs 0.0287 核·s）：6 个均一 worker 各 55% 跑完全部
  worldgen，**它满血时先撞自己的结构墙（6×55%），我们从没逼它到 CPU 极限**。
- 饥饿下差距 19.5% 倒向 C2ME：它 6 worker 87-94% **完美打包**进 3 核；我们 9+ 线程
  拓扑（features 51% + replay 51×2 + pool 21-29×4 + GPU 23）只用了逻辑容量的 70%，
  且 GPU 线程的 FFM/驱动/sync CPU 在饥饿下间歇饱和（busy 尖峰 99.9%）——设备线程
  自己也变成了抖动的串行链。
- 我们的 GPU 确实省了 ~2.9 核的密度+规则算术，但管线把它花回去了：**replay 写方块
  1.4 核 + 调度/体提交 2.0 核 + GC 0.33 + 设备喂入 0.36**。

### 这买到的路线图（每区块 CPU 从 0.0287 → 0.0206 以下的路标）

1. **replay/writeChunk（1.4 核）**：决策 id → 方块状态 → section 的写路径。
   设备直接产出压缩 section 数据是终极形态；批量化是中间形态。
2. **Worker-Main 池（2.0 核）**：SURFACE/CARVERS 体 + 提交开销——与 C2ME 的
   3.28 核全包预算对照，我们的调度层偏肥。
3. **GC 瘦身（0.33）+ 设备喂入 FFM 成本（0.36）**。

做到 0.0206 以下，弱核机器（≤2 物理核）上才会真正反超——当前两者在 3 核下
都还喂得饱。**门一的结论：以当前实现，饥饿区也是 C2ME 的；差距已量化，
靶点已具名，要不要追是范围决策。**

### 补遗：池子膨胀的真身是 vanilla 噪声回退（2026-10-15，密集栈采样）

§27 把池 2.0→4.2 核归因给"调度/补偿 churn"——**错了**。新世界 + 运行中密集栈
采样（30×~1s，jcmd）抓到 `wgen_fill_noise`（vanilla 26.1.2 给 fillFromNoise
命名的池线程，`NoiseBasedChunkGenerator.java:403`）在跑**真正的 vanilla 密度
计算**（Aquifer.computeSubstance、PerlinNoise、ImprovedNoise）。

机制：decideGpu 的 GPU 线程串行 service ~6.3ms（容量 ~145/s）< Chunky 需求
~177/s → fillJobs（ArrayBlockingQueue(64)）饱和 → `offer` 失败 →
`completeExceptionally("the GPU queue is full")` → **该区块整体回退 vanilla
噪声**（handle 兜底，REPORTED_FAILURE 只报一次，之后静默）。证据链：
回退警告恰好 1 条 + decideGpu 场 GPU 份额均值 143/s（非 decideGpu 场 ~178/s
= 100% 设备份额，无回退）+ wgen_fill_noise 采样帧。~20% 区块 × vanilla 全
噪声栈（10-20ms）≈ 0.6-0.9 核，叠加回退块的后续调度——池膨胀主体。

**这改写了决定**：回退是"正确但昂贵"的逃生门——地形仍逐位一致（vanilla 自己
算的），但 CPU 上把我们要省的东西吃了回去。修法两条，合起来 decideGpu 才能
翻正：
1. **背压替代回退**：offer 失败改阻塞 put（wgen_fill_noise 线程等待，管线
   自节流到设备速率；无死锁环——GPU 线程只依赖 replay worker，不依赖池）。
   逃生门保留给设备故障路径（异常回退），饱和回退退役。
2. **杠杆④复活：密度设备驻留**——emitAndDecide 产出的密度先落主机再被
   decider 传回设备（2.4MB 往返 + 两次拷贝）；decideGpu 路径下两者已是同一
   GPU 管线，直连省 ~1.5-2ms GPU 线程 service → 设备容量 ~145 → ~220/s
   > 需求 → 回退彻底消失。
两项落地后预期：replay 0.26 + 池回 ~2.0 + GPU 线程 ~0.3，合计 ~4.1 核
@ ~175 cps ≈ 0.023 核·s/块——贴平 C2ME，饥饿区随核数进一步下降反超。

## 二十八、杠杆④+背压落地：每区块 CPU 反超 C2ME，饥饿差距砍半（2026-10-15）

判读：FEATURES 的 4.5ms 是 vanilla 特征布置的**真实工作总量**，没有契约安全的

(a) ncu 内核归因（工具投资，设备线程 3.4ms 的构成只有猜测）；
(b) 延迟赛道（客户端 regime，需要玩家）；
(c) 收尾打磨（文档、清理、客户端验收）。
